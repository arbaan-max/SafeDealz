# CLAUDE.md — Coding Style & Architecture Guide

This file defines the preferred coding standards, architecture patterns, naming conventions, and implementation expectations for Flutter projects under this setup. Use it both to **bootstrap a new project** and to **add new features/modules** to an existing one.

# Developer Profile & Working Context

The developer is a Flutter-focused application engineer specializing in scalable production-grade mobile applications using Flutter, BLoC architecture, Firebase, Dio, GoRouter, and REST APIs.

Primary focus areas:

- Performance-sensitive Flutter applications
- Subscription-based systems
- Medical/workflow applications
- Firebase-integrated applications
- Large API-driven applications
- Clean scalable architectures

Preferred engineering principles:

- Clean architecture
- Predictable folder structure
- Strict naming consistency
- Readable and maintainable code
- Reusable widgets and abstractions
- Production-ready implementations
- Explicit typing when beneficial
- Minimal overengineering

Preferred Flutter stack:

- flutter_bloc / HydratedBloc
- Dio
- **swagger_parser** → generates Retrofit (Dio) clients from a `swagger.json` spec
- **freezed + json_serializable** → generated, immutable, value-equal DTOs
- **build_runner** → runs the generators
- Firebase
- GoRouter
- Equatable
- Modular widget architecture

Code generated by Claude should prioritize:

1. Scalability
2. Readability
3. Maintainability
4. Performance
5. Consistency with existing architecture

Flutter UI expectations:

- Avoid deeply nested widget trees
- Reduce unnecessary rebuilds
- Prefer modular reusable widgets
- Use const constructors whenever possible
- Keep widgets performant and responsive
- Follow existing BLoC architecture patterns

Important:

- Match the style of the existing codebase
- Reuse existing patterns before introducing new ones
- Avoid unnecessary abstractions
- Avoid large architectural rewrites unless explicitly requested

## ⚠️ CRITICAL — Read Before Touching Anything

> **DO NOT modify the pre-built infrastructure files in `lib/core/interceptors/`, `lib/core/exceptions/`, and the non–design-system files in `lib/core/utils/` (`constants.dart`, `extensions.dart`, `helpers.dart`, `responsive.dart`).**
> These are crafted once by the developer and contain interceptors, constants, extensions, helpers, and utilities.
> **Even if something seems wrong or outdated — do NOT touch them.** If a new utility or constant is needed, ask the developer before adding it.
>
> **EXCEPTION — design-system files you AUTHOR at project startup:**
> `lib/core/utils/theme.dart` (`AppTheme`), `app_colors.dart`, `app_text_styles.dart`, `lib/core/utils/images.dart` (`AppImages`), and `lib/core/utils/icons.dart` (`AppIcons`).
> You write these once when the project is created (brand colors, themes, asset paths — see **§9.4 / §9.5**), then keep them stable. They are NOT pre-built.

> **DO NOT modify any GENERATED file — the API clients and API models.**
> Everything under `lib/data/api/` (generated Dio/Retrofit clients + Freezed DTOs), every generated model, and every `*.g.dart` / `*.freezed.dart` file is produced from the synchronized `swagger/swagger.json`. Never hand-edit generated output or that local spec copy.
> The same applies to every `*.g.dart` and `*.freezed.dart` file anywhere.
> **To change an API model, client method, or endpoint, edit the canonical backend spec and regenerate — never hand-edit the output.** Hand-written service adapters may change only orchestration and error mapping; they must use generated clients and DTOs. See **Sections 5–6**.

> **Files you MUST modify when adding a new feature:**
> `backend/openapi/openapi.json` — add the new endpoint(s) + schema(s), then run `make -f files/Makefile generate-api` from the repository root (Section 5).
> `lib/core/route/routes.dart` — add the new route name constant.
> `lib/core/route/app_router.dart` — add the new `GoRoute` entry.
> `lib/app/app.dart` — register the new `BlocProvider` in `MultiBlocProvider`.
> These are the integration points for every new feature — always update them.

## 2. Naming Conventions

### Files
- All file names are `snake_case`.
- Bloc files: `<feature>_bloc.dart`, `<feature>_event.dart`, `<feature>_state.dart`
- Repository files: `<feature>_repository.dart`
- Service files: `<feature>_service.dart`
- Model files (hand-written domain models): `<feature>.dart` (singular noun, e.g., `user.dart`)
- Entity/Params files: `<feature>_params.dart`
- Screen files: `<feature>.dart` or `<screen_name>.dart`
- Widget files: `<widget_name>.dart` (descriptive noun, e.g., `item_card.dart`, `loading.dart`)
- **Generated files**: produced by the tools — `<schema>.dart`, `<schema>.freezed.dart`, `<schema>.g.dart`, `<tag>_client.dart`. Never renamed or edited by hand.

### Classes
- Bloc: `<Feature>Bloc` — e.g., `SendOTPBloc`, `OrderBloc`
- Event base: `<Feature>Event` — e.g., `SendOTPEvent`
- State base: `<Feature>State` — e.g., `SendOTPState`
- Repository abstract: `<Feature>Repository` — e.g., `AuthRepository`
- Repository impl: `<Feature>RepositoryImpl` — e.g., `AuthRepositoryImpl`
- Service: `<Feature>Service` — e.g., `AuthService`
- Generated client: `<Tag>Client` / `RestClient` (root) — produced by swagger_parser
- Generated DTO: PascalCase singular — e.g., `User`, `Order` (freezed classes)
- Hand-written domain model: PascalCase singular — e.g., `JsonResponse`
- Params/Entity: `<Feature>Params` or `<Feature>ParamsItem` — e.g., `OrderParams`
- Screen widgets: `<Feature>Page` or `<Feature>Screen` — e.g., `AuthPage`
- Reusable widgets: descriptive PascalCase — e.g., `ItemCard`, `Loading`

### Constants
- All top-level constants use the `k` prefix in camelCase: `kURL`, `kAccessToken`
- Route name strings use the suffix `Route`: `authRoute`, `verifyOTPRoute`

### Private methods in Bloc
- Event handler methods are prefixed with `_on`: `_onSendOTPEvent`, `_onVerifyOTPEvent`

## 3. BLoC Architecture — The Non-Negotiable Rules

### 3.1 File Structure — Always Use `part` / `part of`

Every bloc feature has **exactly 3 files**. The event and state files are `part of` the bloc file.

```dart
// send_otp_bloc.dart
part 'send_otp_event.dart';
part 'send_otp_state.dart';
```


```dart
// send_otp_event.dart
part of 'send_otp_bloc.dart';
```


```dart
// send_otp_state.dart
part of 'send_otp_bloc.dart';
```

**NEVER make event or state files standalone — they must always be `part of` the bloc file.**

---

### 3.2 State Pattern — TWO Styles, Pick the Right One

There are **two state patterns** in use. Choose based on the complexity and nature of the bloc.

---

#### 🔵 Style A — Single State Class with `isLoading` / `error` / `message` + `copyWith()`

> **Use this for blocs that:**
> - Hold persistent data across multiple events (e.g., a list, the current user, a cart)
> - Have multiple events that each update different parts of the same state
> - Need to be persisted with `HydratedBloc`
> - Update state granularly without replacing the whole state

```dart
part of '<feature>_bloc.dart';

/// [<Feature>State] holds all state for the <feature> feature.
/// [isLoading] is true when any operation is in progress.
/// [error] is non-empty when an error has occurred.
/// [message] is non-empty when a success message should be shown.
/// [data] holds the primary data for this feature.
class <Feature>State extends Equatable {
  const <Feature>State({
    this.isLoading = false,
    this.error = '',
    this.message = '',
    this.data = const <SomeDto>[],     // ← generated freezed DTO (Section 7)
  });

  final bool isLoading;
  final String error;
  final String message;
  final List<SomeDto> data;

  /// [copyWith] returns a new [<Feature>State] with only the given fields replaced.
  /// All unchanged fields retain their current values.
  <Feature>State copyWith({
    bool? isLoading,
    String? error,
    String? message,
    List<SomeDto>? data,
  }) =>
      <Feature>State(
        isLoading: isLoading ?? this.isLoading,
        error: error ?? this.error,
        message: message ?? this.message,
        data: data ?? this.data,
      );

  @override
  List<Object?> get props => [isLoading, error, message, data];
}
```

> **Why freezed DTOs matter here:** the state's `props` compares `data` element-by-element. Because generated DTOs are **freezed** they implement value `==`/`hashCode`, so a rehydrated state compares equal to a freshly-fetched identical one — no redundant rebuilds. A plain (non-freezed) model would break this. See Section 7.

**When `HydratedBloc` is used**, also add `fromJson` and `toJson` — the freezed DTO already provides `fromJson`/`toJson`, so persistence is trivial:

```dart
/// [fromJson] reconstructs state from persisted storage.
/// Only persist the fields that must survive app restarts.
/// Prefix hydrated keys with 'Hydrated' to distinguish them.
factory <Feature>State.fromJson(Map<String, dynamic> json) => <Feature>State(
      data: (json['HydratedData'] as List?)
              ?.map<SomeDto>((e) => SomeDto.fromJson(e as Map<String, dynamic>))
              .toList() ??
          const <SomeDto>[],
    );

/// [toJson] serializes only the fields that need to be persisted.
Map<String, dynamic> toJson() => {
      'HydratedData': data.map((e) => e.toJson()).toList(),
    };
```

**How to emit with Style A (in the bloc):**

```dart
// Start of any async event handler — clear error/message, show loading
emit(state.copyWith(isLoading: true, error: '', message: ''));

// On success — turn off loading, set message, update data
emit(state.copyWith(
  isLoading: false,
  message: 'Loaded successfully.',
  data: result,
));

// On failure — turn off loading, set error
emit(state.copyWith(isLoading: false, error: response.message));

// On exception catch
emit(state.copyWith(isLoading: false, error: 'Something went wrong'));

// Reset to empty state entirely
emit(const <Feature>State());
```

**UI side with Style A:**

```dart
BlocBuilder<<Feature>Bloc, <Feature>State>(
  builder: (context, state) {
    if (state.isLoading) return const Loading();
    if (state.error.isNotEmpty) { /* show error */ }
    return YourWidget(data: state.data);
  },
)

// For side effects (snackbar, navigation) triggered by message/error changes:
BlocListener<<Feature>Bloc, <Feature>State>(
  listenWhen: (prev, curr) => prev.message != curr.message && curr.message.isNotEmpty,
  listener: (context, state) {
    ScaffoldMessenger.of(context).showSnackBar(
      SnackBar(content: Text(state.message)),
    );
  },
)
```

#### 🟢 Style B — Multiple Subclasses (Abstract base + named subclasses)

> **Use this for blocs that:**
> - Perform a **single, focused action** with a clear start/end (e.g., send OTP, update profile)
> - Do NOT need to hold or accumulate data across events
> - Are simple enough that the state can only ever be one thing at a time

```dart
part of '<feature>_bloc.dart';

/// [<Feature>State] is the abstract base class for all states.
abstract class <Feature>State extends Equatable {
  const <Feature>State();

  @override
  List<Object> get props => [];
}

/// [<Feature>Initial] is the initial/idle state.
class <Feature>Initial extends <Feature>State {}

/// [<Feature>Loading] is emitted immediately when the event fires.
/// Use descriptive present-progressive naming: SendingOTP, VerifyingOTP.
class <Feature>Loading extends <Feature>State {}

/// [<Feature>Success] is emitted when the operation completes successfully.
class <Feature>Success extends <Feature>State {
  const <Feature>Success();
}

/// [<Feature>Failure] is emitted when the operation fails.
/// [message] contains the human-readable error message — always required.
class <Feature>Failure extends <Feature>State {
  const <Feature>Failure({required this.message});
  final String message;

  @override
  List<Object> get props => [message];
}
```

**Rules for Style B:**
- The abstract base always has a `const <Feature>State()` constructor and returns empty `props`.
- `<Feature>Loading` carries no data — it is a pure signal to show a spinner.
- `<Feature>Success` can optionally carry data fields. If it does, override `props` with those fields.
- `<Feature>Failure` **always** has a `required String message` field — never emit a failure without a message.
- States with no data do not override `props`.
- Use `const` constructors everywhere possible.

**How to emit with Style B (in the bloc):**

```dart
emit(<Feature>Loading()); // or emit(SendingOTP())
try {
  final response = await repository.someMethod(event.param);
  if (response.success) {
    emit(const <Feature>Success());
  } else {
    emit(<Feature>Failure(message: response.message));
  }
} catch (_) {
  emit(const <Feature>Failure(message: 'Something went wrong'));
}
```

**UI side with Style B:**

```dart
BlocConsumer<<Feature>Bloc, <Feature>State>(
  listener: (context, state) {
    if (state is <Feature>Success) {
      // navigate or show success feedback
    } else if (state is <Feature>Failure) {
      ScaffoldMessenger.of(context).showSnackBar(
        SnackBar(
          content: Text(state.message),
          backgroundColor: Theme.of(context).colorScheme.error,
        ),
      );
    }
  },
  builder: (context, state) {
    if (state is <Feature>Loading) return const Loading();
    return YourNormalUI();
  },
)
```

#### ✅ Quick Decision Table

| Situation | Use Style |
|---|---|
| Bloc holds a list/object that persists and updates across many events | **A** |
| Bloc uses `HydratedBloc` for persistence | **A** |
| Multiple events update different slices of the same state | **A** |
| Bloc does one simple async action (send, verify, update) | **B** |
| State only ever means one thing at a time (loading OR success OR failure) | **B** |
| Bloc needs `copyWith()` to partially update state | **A** |

### 3.3 Event Pattern

```dart
part of '<feature>_bloc.dart';

/// [<Feature>Event] is the event description.
/// [param] is the description of the parameter.
class <Feature>Event extends Equatable {
  const <Feature>Event({required this.param});
  final String param;

  @override
  List<Object> get props => [param];
}
```

**Rules:**
- All events extend `Equatable`.
- All event parameters must be `final`.
- Use named parameters with `required` for all event fields.
- Override `props` with all fields.
- If an event has no data, it still extends `Equatable` with empty `props`.
- Events that take no parameters can be `const` and passed without `()` when adding.

### 3.4 Bloc Class Pattern

The bloc class structure mirrors the state style chosen in 3.2.

#### Style A Bloc — Single State with `copyWith()`

```dart
import 'dart:async';

import 'package:<app>/data/repositories/<feature>_repository.dart';
import 'package:<app>/data/api/models/<feature_dto>.dart'; // generated freezed DTO
import 'package:equatable/equatable.dart';
import 'package:hydrated_bloc/hydrated_bloc.dart'; // or flutter_bloc if not hydrated

part '<feature>_event.dart';
part '<feature>_state.dart';

/// [<Feature>Bloc] manages the state of <feature>.
/// Uses a single state class updated via [copyWith].
/// [isLoading], [error], and [message] in state signal async operation status.
///
/// Events:
/// 1) [Load<Feature>Event] — fetches data from the server.
/// 2) [Refresh<Feature>Event] — resets and reloads data.
class <Feature>Bloc extends HydratedBloc<<Feature>Event, <Feature>State> {
  <Feature>Bloc({required this.repository}) : super(const <Feature>State()) {
    on<Load<Feature>Event>(_onLoad<Feature>Event);
  }

  final <Feature>Repository repository;

  FutureOr<void> _onLoad<Feature>Event(
      Load<Feature>Event event, Emitter<<Feature>State> emit) async {
    try {
      emit(state.copyWith(isLoading: true, error: '', message: ''));
      final response = await repository.getData();
      if (response.success) {
        final data = response.data as List<<Feature>Dto>;
        emit(state.copyWith(
          isLoading: false,
          data: data,
          message: 'Loaded successfully.',
        ));
      } else {
        emit(state.copyWith(isLoading: false, error: response.message));
      }
    } on Exception catch (e) {
      emit(state.copyWith(isLoading: false, error: e.toString()));
    }
  }

  @override
  <Feature>State? fromJson(Map<String, dynamic> json) =>
      <Feature>State.fromJson(json);

  @override
  Map<String, dynamic>? toJson(<Feature>State state) => state.toJson();
}
```

#### Style B Bloc — Multiple State Subclasses

```dart
import 'dart:async';

import 'package:<app>/data/repositories/<feature>_repository.dart';
import 'package:equatable/equatable.dart';
import 'package:flutter_bloc/flutter_bloc.dart';

part '<feature>_event.dart';
part '<feature>_state.dart';

/// [<Feature>Bloc] manages the state of <feature>.
/// [<Feature>Bloc] extends [Bloc] which takes [<Feature>Event] and returns [<Feature>State].
/// [repository] is the object of [<Feature>Repository].
///
/// States:
/// 1) [<Feature>Initial] — initial idle state.
/// 2) [<Feature>Loading] — operation in progress.
/// 3) [<Feature>Success] — operation completed successfully.
/// 4) [<Feature>Failure] — operation failed with a [message].
///
/// Events:
/// 1) [<Feature>Event] — triggers the operation.
///
/// [_on<Feature>Event] — calls the repository and emits the appropriate state.
class <Feature>Bloc extends Bloc<<Feature>Event, <Feature>State> {
  <Feature>Bloc({required this.repository}) : super(<Feature>Initial()) {
    on<<Feature>Event>(_on<Feature>Event);
  }

  final <Feature>Repository repository;

  FutureOr<void> _on<Feature>Event(
      <Feature>Event event, Emitter<<Feature>State> emit) async {
    emit(<Feature>Loading());
    try {
      final response = await repository.someMethod(event.param);
      if (response.success) {
        emit(const <Feature>Success());
      } else {
        emit(<Feature>Failure(message: response.message));
      }
    } catch (_) {
      emit(const <Feature>Failure(message: 'Something went wrong'));
    }
  }
}
```

**Rules (both styles):**
- Always emit the loading state as the **very first** `emit` inside every async event handler — before `await`.
- Wrap all async logic in `try/catch`.
- The service layer converts the generated client's `DioException` into `JsonResponse.failure(...)` — so the bloc's `catch` is for truly unexpected exceptions only.
- Repository is **always** injected via constructor — never instantiate inside the bloc.
- Dependent blocs (e.g., `UserBloc`) are injected via constructor and declared as `final` fields.
- The `FutureOr<void>` return type is mandatory for all event handlers.
- Event handlers are always private: `_on<Feature>Event`.
- Declare `final` fields (repository, injected blocs) **after** the constructor, not before it.
- **Never** call the generated `RestClient` from a bloc — always go through Service → Repository.

### 3.5 Local Storage Rules

> **Standard for this setup: `HydratedBloc` is the single local-storage mechanism.**
> There is ONE AES-encrypted store (set up in `start.dart`) used for both persisted bloc state and small sensitive values (the access token, current user). `flutter_secure_storage`, `hive`, and `isar` are **not** used by default — only introduce them with explicit developer approval.

**Two uses of the one store:**

1. **Persisted bloc state** — Style A blocs extend `HydratedBloc` and implement `fromJson`/`toJson` (see §3.2 / §3.4). Persist only the fields that must survive a restart (prefix hydrated keys with `Hydrated`).

2. **Token & small auth values** — write/read directly on the storage box using the `k`-prefixed constant keys:

```dart
// Save the token (e.g., after OTP/login success):
await HydratedBloc.storage.write(kAccessToken, user.accessToken);

// Read it (the AuthInterceptor does this to inject the Bearer header):
final token = HydratedBloc.storage.read(kAccessToken) as String?;

// Logout / account deletion — clear EVERYTHING (token + all persisted state):
await HydratedBloc.storage.clear();
```

**Encryption (pre-configured — do NOT modify):** `start.dart` builds `HydratedBloc.storage` with `HydratedAesCipher` (key derived from `kPassword` via `sha256`), backed by the app support directory. The token therefore lives in an **encrypted** box, not in the OS keychain.

**Rules:**
- Initialize `HydratedBloc.storage` before `runApp()` (already done in `start.dart` — do not touch).
- **Never** access `HydratedBloc.storage` directly from UI — do it inside a bloc.
- The access token is read by `AuthInterceptor` only (§5 / §6) — UI/blocs never build the `Authorization` header themselves.
- Persist only the minimum necessary data; never persist large blobs (lists of full DTOs are fine, raw images/files are not).
- Storage failures must never crash the app — guard reads with null-safe casts and fallbacks.


### 3.6 Inter-Bloc Communication

When one bloc depends on another (e.g., `VerifyOTPBloc` depends on `UserBloc`):

```dart
class VerifyOTPBloc extends Bloc<VerifyOTPEvent, VerifyOTPState> {
  VerifyOTPBloc({
    required this.authRepository,
    required this.userBloc,
  }) : super(VerifyOTPInitial()) {
    on<VerifyOTPEvent>(_onVerifyOTPEvent);
  }

  FutureOr<void> _onVerifyOTPEvent(
      VerifyOTPEvent event, Emitter<VerifyOTPState> emit) async {
    emit(VerifyingOTP());
    try {
      final response = await authRepository.verifyOTP(event.phone, event.otp);
      if (response.success) {
        final user = response.data as User;
        userBloc.add(SaveUser(user: user));            // ← cross-bloc event dispatch
        await HydratedBloc.storage.write(kAccessToken, user.accessToken);
        emit(const VerifyOTPSuccess());
      } else {
        emit(VerifyOTPFailure(message: response.message));
      }
    } on Exception catch (e) {
      emit(VerifyOTPFailure(message: 'Error: $e'));
    }
  }

  final AuthRepository authRepository;
  final UserBloc userBloc;
}
```

**Rules:**
- Only call `otherBloc.add(SomeEvent(...))` — **never** access another bloc's state directly inside a bloc.
- Dependent blocs are always injected via constructor.
- Declare injected blocs as `final` fields.

#### 3.7.1 Which host does the app actually talk to? (`localhost` is not one thing)

`kURL` is composed in `lib/core/utils/constants.dart` via `resolveApiHost()`. `.env` keeps `BASE_URL=localhost:5099` for every target; the resolver corrects it per platform:

| Target | Resolved host | Why |
|---|---|---|
| iOS sim · macOS · Windows · Linux | `localhost:5099` | they share the Mac's loopback |
| Android **emulator** | `10.0.2.2:5099` | the emulator's loopback is the EMULATOR — `10.0.2.2` is its alias for the host |
| Android **real device** | whatever `--dart-define=API_HOST` says | it has neither the Mac's loopback nor the `10.0.2.2` alias |

**`--dart-define=API_HOST=host:port` wins over `.env` and is never rewritten.** That is the ONLY way to run on a real device — without it the phone resolves `10.0.2.2`, which means nothing to it, and every request fails with no obvious cause.

**Real device — use the script, don't hand-edit `.env`:**
```bash
cd spa && ./tool/run_device.sh          # adb tunnel (USB *or* wireless) + the right --dart-define
./tool/run_device.sh --lan             # reach the Mac by LAN IP instead (same network)
./tool/run_device.sh --port 5099       # backend on another port
./tool/run_device.sh --device <serial> # only when two DIFFERENT phones are attached
```
It defaults to `adb reverse tcp:PORT tcp:PORT`, mapping the DEVICE's `localhost:PORT` to the Mac's: no LAN IP to look up, no macOS firewall prompt, and nothing breaks when Wi-Fi reassigns your IP. **It works over wireless debugging too** — verified on a QR-paired phone; `adb reverse` tunnels through the adb connection whatever the transport is. It refuses to start when the backend isn't answering, so you get a reason instead of a dead app.

**Wireless debugging registers ONE phone as TWO adb devices** — an mDNS `adb-<serial>-xxxx._adb-tls-connect._tcp` transport *and* an `ip:port` one. Counting adb lines therefore reports "two devices" and bails (this cost a debugging round: the script refused to run → the fallback was a plain `flutter run` → the app silently talked to `10.0.2.2` and every request vanished). The script dedupes on `ro.serialno`: one handset is one device however many ways it is attached.

**Which mode when:**
- **adb tunnel (default)** — nothing to configure, but it dies with the adb connection: unplug the cable or drop wireless debugging and the app can no longer reach the backend.
- **`--lan`** — survives adb disconnecting, so use it when handing the phone to someone. Needs the phone on the same network and macOS to allow incoming connections to node, and it breaks when DHCP moves your IP.

**Do not "fix" this by pointing `.env` at a LAN IP** — `.env` is a bundled asset (needs a full restart, not hot reload), it is shared with the emulator/CI, and the IP goes stale. Pass `API_HOST`. Covered by `test/api_host_test.dart`.

### 3.8 Pagination Standard (infinite scroll)

> Every paginated list/feed uses the SAME shape so projects don't reinvent it. This mirrors the reference (`project_setup_ref` → `ItemBloc` / `ItemState` + the `infiniteItems({int page = 0, int limit})` service): **page-based, page starts at 0, results accumulate into one list, the page resets on a new query/filter, and you stop when a short page returns.**

**State (Style A) — required pagination fields:**

```dart
class NewsState extends Equatable {
  const NewsState({
    this.articles = const <Article>[],   // accumulated list (grows as you page)
    this.page = 0,                        // current page — starts at 0
    this.limit = 20,                      // page size
    this.isLoading = false,               // first page / refresh spinner
    this.isLoadingMore = false,           // appending the next page (footer spinner)
    this.hasMore = true,                  // false once a short/empty page returns
    this.error = '',
  });

  final List<Article> articles;
  final int page;
  final int limit;
  final bool isLoading;
  final bool isLoadingMore;
  final bool hasMore;
  final String error;

  // standard copyWith over ALL fields (see §3.2)
  NewsState copyWith({ /* … */ }) => /* … */;

  @override
  List<Object> get props =>
      [articles, page, limit, isLoading, isLoadingMore, hasMore, error];
}
```

> The reference uses `isEnd` (= `!hasMore`) and reuses a single `isLoading`. This standard splits **`isLoading`** (first page) from **`isLoadingMore`** (appending) so the UI can show a list spinner vs. a bottom-footer spinner. Either naming is fine — just stay consistent across the app.

**Bloc — first load, load-more, and refresh in one handler:**

```dart
FutureOr<void> _onLoadNewsEvent(LoadNewsEvent event, Emitter<NewsState> emit) async {
  // Guard: ignore load-more when already appending or no more pages.
  if (event.loadMore && (state.isLoadingMore || !state.hasMore)) return;

  final isFirst = !event.loadMore;
  final nextPage = isFirst ? 0 : state.page + 1;

  emit(state.copyWith(
    isLoading: isFirst,
    isLoadingMore: !isFirst,
    error: '',
  ));

  try {
    final response = await repository.getNews(page: nextPage, limit: state.limit);
    if (response.success) {
      final fetched = response.data as List<Article>;
      emit(state.copyWith(
        articles: isFirst ? fetched : <Article>[...state.articles, ...fetched],
        page: nextPage,
        hasMore: fetched.length == state.limit,   // short page ⇒ end reached
        isLoading: false,
        isLoadingMore: false,
      ));
    } else {
      emit(state.copyWith(isLoading: false, isLoadingMore: false, error: response.message));
    }
  } on Exception catch (e) {
    emit(state.copyWith(isLoading: false, isLoadingMore: false, error: e.toString()));
  }
}
```

**Service / Repository — always carry `page` + `limit`** (matches the reference `infiniteItems`):

```dart
// Repository (abstract): Future<JsonResponse> getNews({int page = 0, int limit = 20});
// Service: passes {'page': page, 'limit': limit, ...filters} to the generated client / Dio.
```

**UI — trigger load-more from a `ScrollController` near the bottom** (reference uses the 80% threshold):

```dart
scrollController.addListener(() {
  final pos = scrollController.position;
  if (pos.pixels > 0.8 * pos.maxScrollExtent &&
      !context.read<NewsBloc>().state.isLoadingMore &&
      context.read<NewsBloc>().state.hasMore) {
    context.read<NewsBloc>().add(const LoadNewsEvent(loadMore: true));
  }
});
```

**Rules:**
- `page` starts at **0**; results **accumulate** into one list (`[...old, ...new]`).
- A **new query/filter resets** `page` to 0, clears the list, and sets `hasMore: true`.
- Stop paging when a page returns **fewer than `limit`** items → `hasMore = false`.
- Guard load-more against re-entry: `if (state.isLoadingMore || !state.hasMore) return;`.
- Trigger from the scroll position (~**80%** of `maxScrollExtent`), never a fixed item index.
- Pagination state lives in the bloc (Style A) — the UI only reads it and dispatches `loadMore`.

### 3.9 Search Debounce Standard

> ⚠️ **SUPERSEDED for THIS project's search fields (P9D, developer directive 2026-07-19): search fires ON SUBMIT** (`textInputAction: TextInputAction.search` + `onSubmitted`), not on a debounce. `onChanged` handles only the CLEARED case (empty box → reset the list immediately). This applies to the leads search (M3), the owner customers search (O15) and the New Entry customer search. The debounce guidance below remains the default for any *future* live-filtering input that is not one of these.

> **All search inputs MUST debounce. Default debounce = 500 ms. NEVER call the API on every keystroke.** (The reference uses 600 ms via rxdart; **500 ms is the standard** — keep it consistent project-wide. Debouncing alone saves large backend costs.)

Two accepted mechanisms — pick one per project:

**A) rxdart subject in the widget** (reference style — `search.dart`):

```dart
final _onChange = PublishSubject<String>();

@override
void initState() {
  super.initState();
  _onChange.debounceTime(const Duration(milliseconds: 500)).listen((q) {
    final query = q.trim();
    if (query.length < 3) return;                          // min length guard
    if (context.read<NewsBloc>().state.isLoading) return;  // skip if already loading
    context.read<NewsBloc>().add(SearchNewsEvent(query));
  });
}

// TextField(onChanged: (v) => _onChange.add(v))

@override
void dispose() {
  _onChange.close();
  searchController.dispose();
  super.dispose();
}
```

**B) bloc event transformer** (debounce inside the bloc; UI stays dumb) — rxdart on the event stream:

```dart
on<SearchNewsEvent>(
  _onSearchNewsEvent,
  transformer: (events, mapper) =>
      events.debounceTime(const Duration(milliseconds: 500)).switchMap(mapper),
);
```

**Rules:**
- Debounce window: **500 ms** default. Do not fire the API per keystroke.
- Minimum query length **3** before hitting the API (shorter ⇒ ignore).
- Skip dispatch while a search is already in flight (`state.isLoading`).
- Always `trim()` the query; treat empty/cleared input as "reset to the default list".
- Dispose the rxdart subject / controllers in `dispose()`.

## 4. Repository Pattern

### 4.1 Abstract + Implementation

Every repository has an **abstract class** and a **concrete Impl class** in the same file:

```dart
import 'package:<app>/data/models/json_response.dart';
import 'package:<app>/data/services/<feature>_service.dart';

/// [<Feature>Repository] defines the contract for <feature> operations.
abstract class <Feature>Repository {
  /// [methodName] description of what it does.
  Future<JsonResponse> methodName({
    required String param1,
    int param2 = 0,
  });
}

class <Feature>RepositoryImpl implements <Feature>Repository {
  const <Feature>RepositoryImpl({required this.<feature>Service});
  final <Feature>Service <feature>Service;

  @override
  Future<JsonResponse> methodName({
    required String param1,
    int param2 = 0,
  }) =>
      <feature>Service.methodName(param1: param1, param2: param2);
}
```

**Rules:**
- The abstract class documents every method with `///` doc comments.
- The `Impl` class uses a `const` constructor.
- The `Impl` class simply delegates to the service — **no business logic** inside the impl.
- The `Impl` class always uses arrow (`=>`) syntax for single-expression overrides.
- Method signatures in the abstract and impl must match exactly, including optional/named parameters and defaults.
- Return type is always `Future<JsonResponse>` (from `json_response.dart`).
- Inject the service via a required named parameter in the constructor.

### 4.2 Concrete example & the no-logic rule

```dart
import 'package:<app>/data/models/json_response.dart';
import 'package:<app>/data/services/news_service.dart';

/// [NewsRepository] defines the contract for news operations.
abstract class NewsRepository {
  /// [getNews] fetches a page of news articles.
  Future<JsonResponse> getNews({int page = 0, int limit = 20});
}

class NewsRepositoryImpl implements NewsRepository {
  const NewsRepositoryImpl({required this.newsService});

  final NewsService newsService;

  @override
  Future<JsonResponse> getNews({int page = 0, int limit = 20}) =>
      newsService.getNews(page: page, limit: limit);
}
```

**Rule — keep repositories logic-free (the layering contract):**
- A repository contains **NO business logic**. Every method is a one-line delegate to the matching service method.
- **Business logic belongs in the Bloc** — deciding what to fetch, paging/merging lists, branching on results, mapping to states.
- **HTTP + error→`JsonResponse` mapping belongs in the Service** (§6).
- If you feel the urge to transform, branch, combine, or cache data inside an `Impl` method — that logic belongs in the bloc (or service), never the repository.

## 5. API Code Generation (`swagger_parser` → Dio + freezed)

> **This is the single source of truth for all API request/response types, client methods, and HTTP endpoint definitions.**
> The networking client and every API model (DTO) are GENERATED from `backend/openapi/openapi.json`, synchronized to each app's `swagger/swagger.json`, using `swagger_parser` + `build_runner`. They emit Retrofit client declarations/implementations running on Dio and Freezed JSON models. Never hand-write API clients, API DTOs, or raw Dio calls for endpoints represented by the contract.

### 5.1 The pipeline

```
backend/openapi/openapi.json               (canonical backend OpenAPI contract)
        │
        ▼  make -f files/Makefile generate-api  (syncs and generates all three apps)
swagger/swagger.json                       (per-app synchronized input — do not edit by hand)
        │
        ▼  dart run swagger_parser          (spec → Retrofit @RestApi interfaces + freezed models)
lib/data/api/                     (generated client declarations + DTO sources)
        │
        ▼  dart run build_runner build      (Retrofit + freezed + json_serializable → *.g.dart / *.freezed.dart)
lib/data/api/                     (generated client implementations + models ready to use)
        │
        ▼  (you wire the rest of the flow around the generated output)
Service wrapper → Repository → Bloc → UI
```

> After `build_runner` runs, clients and models are generated. A thin service wrapper outside `lib/data/api/` constructs the generated client, maps Dio failures, and returns `JsonResponse`; repositories remain one-line delegates. Never hand-edit generated output.

Run BOTH commands, in order, after any spec change:

```bash
dart run swagger_parser
dart run build_runner build --delete-conflicting-outputs
```

### 5.4 Where the spec lives & how to evolve the API

- The editable contract is `backend/openapi/openapi.json`, served by the backend at `/api-docs/swagger.json`. Each app's `swagger/swagger.json` is a synchronized generator input and must not be edited directly.
- To **add or change an endpoint or model**: edit `backend/openapi/openapi.json` → run `make -f files/Makefile generate-api` from the repository root → use the new generated method/DTO.
- **Never** add a hand-written model or a manual `dio` call for something the spec can describe. If the backend has no spec entry yet, add it to the spec first.

### 5.5 Generated-code rules

- Everything under `lib/data/api/` and every `*.g.dart` / `*.freezed.dart` is **generated** — DO NOT EDIT.
- Pick ONE policy and stick to it: **commit** generated code, OR regenerate in CI. Do not mix.
- All custom logic (interceptors, `DioFactory`, services, repositories, `JsonResponse`) lives in **non-generated** files so regeneration never clobbers it.
- The generated Retrofit client **throws `DioException`** on non-2xx and returns **typed DTOs** on success — it does NOT return `JsonResponse`. The **Service** layer adapts it (Section 6).

### 5.6 Integration notes & caveats

- **Auth stays in interceptors, not generated code.** The generated client is auth-agnostic; the `Dio` it runs on carries the application interceptors built by `DioFactory`. SafeDealz must use one bounded refresh attempt, prevent concurrent refresh storms, validate current account status during refresh, and clear credentials plus redirect to Login immediately when the backend reports an inactive account. Never retry refresh recursively or indefinitely.
- **Response envelope.** If the backend wraps payloads as `{ success, data, ... }`, either model that envelope in the spec, or unwrap `response.data['data']` inside the Service before returning. Generated DTOs must match the shape they actually deserialize.
- **Null-safety accuracy.** Generated DTOs are only as correct as the spec. Mark fields the backend may omit as `nullable`/optional in the spec rather than patching generated code.
- **Multipart / file uploads.** Verify the generator emits proper `@MultiPart`/`@Part` (Retrofit) for upload endpoints and test those specifically — OAS multipart mapping is a common rough edge.

## 6. Service Pattern (wraps the generated client)

> `swagger_parser` and `build_runner` generate clients and DTOs under `lib/data/api/`; they do not generate SafeDealz service wrappers. Services under `lib/data/services/` are thin hand-written adapters that construct or receive the generated client, map failures, and return the repository contract. Do not declare endpoints, duplicate API DTOs, or make raw Dio endpoint calls in a service.

The Service no longer makes raw `dio.get/post` calls. Instead it:
1. Builds a configured `Dio` via **`DioFactory`** (base options + interceptors).
2. Constructs the **generated Retrofit client** from that `Dio`.
3. Calls the generated methods and converts the result / thrown `DioException` into the uniform **`JsonResponse`**.

### 6.1 `DioFactory` (`lib/core/network/dio_factory.dart`)

A single place that produces a consistently-configured `Dio`, so services don't re-configure Dio by hand and the app no longer spawns dozens of ad-hoc `Dio()` instances.

```dart
import 'package:dio/dio.dart';
import 'package:<app>/core/interceptors/auth_interceptor.dart';
import 'package:<app>/core/interceptors/x_client_interceptor.dart';
import 'package:<app>/core/utils/constants.dart';

/// [DioFactory] builds a consistently-configured [Dio].
/// [XClientInterceptor] is always added; [AuthInterceptor] (Bearer token) is
/// added when [authenticated] is true. The returned [Dio] is what the
/// generated Retrofit clients run on, so auth lives here — not in generated code.
class DioFactory {
  const DioFactory._();

  static Dio create({bool authenticated = true}) {
    final dio = Dio(
      BaseOptions(
        baseUrl: kURL,
        sendTimeout: const Duration(seconds: 10),
        receiveTimeout: const Duration(seconds: 10),
        connectTimeout: const Duration(seconds: 10),
        responseType: ResponseType.json,
        headers: const {
          'Content-Type': 'application/json',
          'Accept': 'application/json',
        },
      ),
    );
    dio.interceptors.add(XClientInterceptor());
    if (authenticated) dio.interceptors.add(AuthInterceptor());
    return dio;
  }
}
```

### 6.2 Service class structure

```dart
import 'package:dio/dio.dart';
import 'package:<app>/core/exceptions/dio_exception.dart';
import 'package:<app>/data/api/clients/<feature>_client.dart'; // GENERATED
import 'package:<app>/data/api/models/<feature>_dto.dart';      // GENERATED freezed DTO
import 'package:<app>/data/models/json_response.dart';

/// [<Feature>Service] wraps the GENERATED [<Feature>Client] and converts its
/// typed results / thrown [DioException]s into the uniform [JsonResponse].
class <Feature>Service {
  <Feature>Service({required this.dio}) : _client = <Feature>Client(dio);

  final Dio dio;
  final <Feature>Client _client;

  Future<JsonResponse> getThing({required String id}) async {
    try {
      final <Feature>Dto dto = await _client.getThing(id); // generated; throws on non-2xx
      return JsonResponse.success(message: 'Success', data: dto);
    } on DioException catch (error) {
      final message = DioExceptionOf.exceptionFromDioError(error).errorMessage;
      return JsonResponse.failure(
        statusCode: error.response?.statusCode ?? 500,
        message: 'Error: $message',
      );
    } on Exception {
      return JsonResponse.failure(
        statusCode: 500,
        message: 'Error: Unexpected error occurred.',
      );
    }
  }
}
```

**Rules:**
- The `Dio` is injected via constructor (built by `DioFactory.create(...)` at the wiring site in `app.dart`) — **never** call `Dio()` directly in a service.
- Construct the generated client in the initializer list / constructor body — never inside individual methods.
- **All Service methods return `Future<JsonResponse>`** — never return a raw DTO or `Response` to the repository/bloc.
- Always handle the two failure layers: `on DioException` (use `DioExceptionOf.exceptionFromDioError(error).errorMessage`) and `on Exception` (generic fallback). The success branch wraps the generated DTO via `JsonResponse.success(data: dto)`.
- If the backend wraps responses in an envelope and the spec models the inner shape, unwrap here before constructing `JsonResponse`.
- Do **not** add interceptors or set timeouts inside the service — that is `DioFactory`'s job.

## 7. Model Pattern

### 7.1 API DTOs are GENERATED (freezed) — do not hand-write them

All API request and response models are **generated freezed DTOs** under `lib/data/api/models/` (Section 5). They are produced from the synchronized OpenAPI contract and provide, for free:

- `const` constructor + immutable `final` fields
- `copyWith()`
- value equality (`==` / `hashCode`) — critical for `HydratedBloc` state comparison (Section 3.2)
- `fromJson` / `toJson` (via json_serializable under freezed)

**Never** hand-write, hand-edit, or duplicate a DTO that the spec can describe. To change one, edit the spec and regenerate.

> **HydratedBloc fit:** freezed DTOs serialize cleanly (`toJson`/`fromJson` for persistence) **and** compare by value, so a rehydrated list equals a freshly-fetched identical list — no spurious rebuilds. This is why this setup standardizes on **freezed** (not plain json_serializable) for DTOs.

### 7.2 Hand-written domain models (rare)

Only hand-write a model in `lib/data/models/` when it is a **local/domain type with no spec entry** (e.g., a UI-only composite). When you must, follow this pattern and extend `Equatable`:

```dart
import 'package:equatable/equatable.dart';

/// [ModelName] represents a <description>. (Hand-written domain model only —
/// API DTOs are generated; see Section 5.)
class ModelName extends Equatable {
  const ModelName({
    required this.id,
    this.name,
    this.createdAt,
  });

  final String id;
  final String? name;
  final DateTime? createdAt;

  factory ModelName.fromJson(Map<String, dynamic> json) => ModelName(
        id: json['_id']?.toString() ?? '',
        name: json['name']?.toString(),
        createdAt: DateTime.tryParse('${json['createdAt']}'),
      );

  Map<String, dynamic> toJson() => {
        '_id': id,
        'name': name,
        'createdAt': createdAt?.toIso8601String(),
      };

  ModelName copyWith({String? id, String? name, DateTime? createdAt}) => ModelName(
        id: id ?? this.id,
        name: name ?? this.name,
        createdAt: createdAt ?? this.createdAt,
      );

  @override
  List<Object?> get props => [id, name, createdAt];
}
```

**Rules for hand-written domain models:**
- Extend `Equatable`, all fields `final`, include `const` ctor, `fromJson`, `toJson()`, `copyWith()`, full `props`.
- Use `?.toString()` for strings, `DateTime.tryParse('${json['field']}')` for dates, `int.tryParse`/`double.tryParse`/`num.tryParse`/`bool.tryParse` for numerics — never direct casts.
- For nested/list fields, parse defensively.

### 7.3 `JsonResponse` — Universal Wrapper

This model is **pre-built and must never be modified**. It is the **only return type** for service methods.

```dart
// Usage in services (wrapping a generated DTO):
return JsonResponse.success(message: 'Done', data: generatedDto);
return JsonResponse.failure(statusCode: 404, message: 'Not found');
return JsonResponse.created(message: 'Created', data: generatedDto);

// Usage in bloc:
if (response.success) {
  final dto = response.data as <Feature>Dto;
  emit(<Feature>Success(data: dto));
} else {
  emit(<Feature>Failure(message: response.message));
}
```

## 8. Entity / Params Pattern (`data/entity/`)

> **Prefer generated request DTOs.** When the spec defines a request body, `swagger_parser` generates a freezed DTO for it — use that. Hand-written Params classes are only for request bodies/local payloads **not covered by the spec**.

For those spec-less cases, Params classes are **mutable** and do **not** extend `Equatable`:

```dart
class <Feature>Params {
  <Feature>Params({
    required this.field1,
    required this.field2,
    this.optionalField,
  });

  String field1;
  String field2;
  String? optionalField;

  Map<String, dynamic> toJson() => {
        'field1': field1,
        'field2': field2,
        'optionalField': optionalField,
      };

  <Feature>Params copyWith({
    String? field1,
    String? field2,
    String? optionalField,
  }) {
    return <Feature>Params(
      field1: field1 ?? this.field1,
      field2: field2 ?? this.field2,
      optionalField: optionalField ?? this.optionalField,
    );
  }
}
```

**Rules:**
- Entity/Params classes live in `data/entity/` — **not** in `data/models/` or `data/api/`.
- They are mutable — fields are **not** `final`.
- They do **not** extend `Equatable`.
- They always have `toJson()` and `copyWith()`.
- They do **not** have `fromJson()` — they are outbound-only (request bodies).

## 9. UI / Screen Pattern

### 9.1 Screen Widget Structure

```dart
class <Feature>Page extends StatefulWidget {
  const <Feature>Page({super.key});

  @override
  State<<Feature>Page> createState() => _<Feature>PageState();
}

class _<Feature>PageState extends State<<Feature>Page> {
  // Controllers and local state declared here
  final _controller = TextEditingController();

  @override
  void dispose() {
    _controller.dispose();
    super.dispose();
  }

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      body: BlocConsumer<<Feature>Bloc, <Feature>State>(
        listener: (context, state) {
          if (state is <Feature>Success) {
            // navigation, snackbar, etc.
          } else if (state is <Feature>Failure) {
            ScaffoldMessenger.of(context).showSnackBar(
              SnackBar(
                content: Text(state.message),
                backgroundColor: Theme.of(context).colorScheme.error,
              ),
            );
          }
        },
        builder: (context, state) {
          if (state is <Feature>Loading) {
            return const Loading();
          }
          return // normal UI
        },
      ),
    );
  }
}
```

### 9.2 `BlocConsumer` vs `BlocBuilder` vs `BlocListener`

| Widget | When to use |
|---|---|
| `BlocConsumer` | When you need **both** side effects (navigation, snackbar) **and** UI rebuilds |
| `BlocBuilder` | When you need **only** UI rebuilds, no side effects |
| `BlocListener` | When you need **only** side effects, no UI rebuild |

**Rules:**
- Use `BlocConsumer` as the default for screens that make API calls (the listener handles side effects, the builder handles UI).
- Use `buildWhen` on `BlocBuilder` when rebuilds should be selective to avoid unnecessary redraws.
- Always handle `<Feature>Loading` state in the builder — show a loading widget, never leave it unhandled.
- Always handle `<Feature>Failure` state in the listener — show a `SnackBar` with `state.message`.
- Access blocs with `context.read<<Feature>Bloc>()` when **dispatching events** (inside callbacks).
- Access blocs with `BlocProvider.of<<Feature>Bloc>(context)` when **reading state** outside a builder.
- **Never** call `context.read<>()` or `BlocProvider.of<>()` inside a `build()` method for state reading — use `BlocBuilder` or `BlocConsumer` for that.

### 9.3 Dispatching Events from UI

```dart
// Correct — inside a button callback or gesture:
context.read<SendOTPBloc>().add(
  SendOTPEvent(phone: phone.text.trim()),
);

// Correct — on init:
context.read<SomeBloc>()..add(const LoadEvent());
```

### 9.4 Theme — the global `AppTheme` class

The design system is a **single global class `AppTheme`** in `lib/core/utils/theme.dart`, authored once at project startup. It holds the brand color constants and exposes `lightTheme` / `darkTheme` as `ThemeData` getters. The `MaterialApp` in `app.dart` consumes them via `theme:` / `darkTheme:` / `themeMode:`. Screens then read everything through `Theme.of(context)`.

```dart
// lib/core/utils/theme.dart
import 'package:flutter/material.dart';
```

**Wire it into `MaterialApp` in `app.dart`** (also see §10.3):

```dart
MaterialApp.router(
  debugShowCheckedModeBanner: false,
  theme: AppTheme.lightTheme,
  darkTheme: AppTheme.darkTheme,
  themeMode: ThemeMode.system,   // or drive from a ThemeBloc/Cubit (Style A, HydratedBloc)

```

**Rules:**
- `AppTheme` is the ONLY place that defines colors and `ThemeData`. Author it at startup; never scatter theme values across widgets.
- Keep light/dark in sync by sharing private builders (`_textTheme`, `_inputDecorationTheme`, `_elevatedButtonTheme`) as above.
- For user-selectable themes, drive `themeMode` from a `ThemeBloc`/`Cubit` (Style A, persisted with `HydratedBloc`) and rebuild `MaterialApp` inside a `BlocBuilder`.

#### 9.4.1 Where Material's defaults do NOT match the design system

Two components look plausible out of the box and are still wrong. Both bit us in review (2026-07-17):

**Filter chips → always `AppFilterChip` (`view/widgets/app_chips.dart`), never a raw `ChoiceChip`.**
M3's ChoiceChip renders a pale `secondaryContainer` fill, a dark label and a leading ✓ when selected. The design system (`.fchip`/`.fchip.on`) is: unselected = white + 1px `AppTheme.border` + `textSecondary`; selected = **solid `AppTheme.primary` + white label, no checkmark**; 13px/w600, radius 20, padding 8×15, laid out by `AppFilterChipBar` with 8px gaps. This covers Today/Week/Month/Custom and the lead-status filters on **every** flow (owner · manager · marketing). Pinned by `test/app_chips_test.dart`.
*Exception:* the O1 dashboard's chips sit on the dark-green header and are white-on-dark by design — their own widget, deliberately not this one.

**Anything anchored to the BOTTOM of the screen must clear the gesture bar.** Reported 2026-07-20: the sticky "Create Spa" button on Add New Spa drew *underneath* the Android gesture bar, and every other form's submit had the same bug. Three cases, three tools:

| Case | Use |
|---|---|
| A control pinned below a scrolling body (form submits) | **`StickyBottomBar`** (`view/widgets/sticky_bottom_bar.dart`) — never a bare `Padding` |
| A scrolling body whose last row reaches the screen edge (detail pages) | **`scrollSafePadding(context)`** as the scroll view's `padding` |
| A `showModalBottomSheet` | `SafeArea(top: false)` + `viewInsets` — see below |

`StickyBottomBar` deliberately does **not** add `viewInsets`: it lives inside a `Scaffold`, which already resizes for the keyboard, so adding it would leave a keyboard-sized gap. A modal sheet floats above the Scaffold and therefore must dodge the keyboard itself — hence the different rule. Shell tabs need neither: Material's `NavigationBar` insets itself, and the Scaffold consumes the bottom padding for its body. Pinned by the `P10c gesture-bar insets` tests, which simulate a 48px gesture bar.

**Every `showModalBottomSheet` gets `SafeArea(top: false)`.**
A sheet draws behind the system gesture bar, so a bottom-anchored submit button ends up under it — the O18 export sheet shipped that way. Pad for BOTH:
```dart
builder: (ctx) => SafeArea(
  top: false,                                        // gesture bar
  child: Padding(
    padding: EdgeInsets.fromLTRB(16, 0, 16,
        MediaQuery.of(ctx).viewInsets.bottom + 16),  // keyboard
    child: ...,
  ),
),
```
They never double-count: `MediaQuery.padding` (what SafeArea uses) is already reduced by `viewInsets`.

**Tinted "highlight" rows are INSET, never edge-to-edge.** A `Container(color:)` filling a row inside a `Card` runs under the card's rounded corners and reads as a broken bar. Give it `margin` + its own `borderRadius` (see `_BySpaRow` in `reports_page.dart`, prototype O17: `border-radius:9px`).

### 9.5 Assets — `AppImages` & `AppIcons`

```dart
// lib/core/utils/icons.dart
/// [AppIcons] holds every SVG / icon asset path.

class AppIcons {
```

### 9.6 Using theme & assets in widgets — rules

```dart
// ✅ Correct
Theme.of(context).colorScheme.primary
Theme.of(context).textTheme.bodyLarge
Image.asset(AppImages.logo)
SvgPicture.asset(AppIcons.comment)

// ❌ Wrong
Colors.blue

SvgPicture.asset('assets/svg/message.svg')   // inline path
```

- Never use hardcoded `Colors.*` in screens or widgets — derive from `Theme.of(context).colorScheme.*`.
- Derive text styles from `Theme.of(context).textTheme.*`, then `.copyWith()` if modification is needed.
- Reference a raw brand color via `AppTheme.primary` ONLY when no `colorScheme` slot fits (e.g., a fixed brand splash); otherwise prefer `Theme.of(context)`.
- Reference every asset via `AppImages` / `AppIcons` — never an inline path.
- Use `MediaQuery.of(context).size` or the `responsive.dart` helpers (`compact()`, `medium()`, `responsivePadding()`) for responsive layout.

### 9.7 Prefer Slivers for Scrollable Content

> **Default to slivers for anything that scrolls.** Build scrollable screens with a `CustomScrollView` composed of sliver widgets instead of a `SingleChildScrollView` + `Column` or a bare `ListView`. Slivers share one scroll context, so a header, a list, a grid, and a footer scroll together — lazily and without nested scroll views.

**Use the sliver equivalent of the plain widget:**

| Instead of | Use |
|---|---|
| `SingleChildScrollView` + `Column` | `CustomScrollView` + `SliverList` / `SliverToBoxAdapter` |
| `ListView` / `ListView.builder` | `SliverList` / `SliverList.builder` |
| `GridView` / `GridView.builder` | `SliverGrid` / `SliverGrid.builder` |
| `AppBar` that scrolls/collapses | `SliverAppBar` (`pinned` / `floating` / `snap`) |
| A single non-list widget in the scroll | `SliverToBoxAdapter` |
| Padding around a scrollable section | `SliverPadding` |
| Fill leftover viewport (empty / error states) | `SliverFillRemaining` |

```dart
CustomScrollView(
  controller: scrollController,      // same controller used for pagination (§3.8)
  slivers: [
    const SliverAppBar(pinned: true, title: Text('Feed')),
    SliverPadding(
      padding: const EdgeInsets.all(16),
      sliver: SliverList.builder(
        itemCount: state.articles.length,
        itemBuilder: (context, i) => ArticleCard(article: state.articles[i]),
      ),
    ),
    if (state.isLoadingMore)
      const SliverToBoxAdapter(child: Loading()),
  ],
)
```

**Rules:**
- Scrollable screens use `CustomScrollView` + slivers; reach for `SingleChildScrollView` / `Column` only for small, fixed, non-list content that never needs a second scrollable section.
- A plain `ListView` is acceptable for a single simple list with nothing else scrolling; the moment you combine a header, multiple lists, or a collapsing app bar, switch to slivers.
- Pagination (§3.8) is unchanged — attach the same `ScrollController` to the `CustomScrollView`, keep the ~80% `maxScrollExtent` load-more trigger, and render the footer spinner as a `SliverToBoxAdapter`.
- Never nest a scrollable inside another scrollable to stitch sections together — compose them as slivers.
- Use `const` sliver constructors wherever possible.

## 10. App Bootstrap & `MultiBlocProvider` Setup

### 10.1 `app/start.dart` — Entry Point

`startApplication()` is always called from `main.dart`:

```dart
// main.dart
void main() => startApplication(() => const Application());
```

This handles:
1. `WidgetsFlutterBinding.ensureInitialized()`
2. Firebase initialization
3. HydratedBloc encrypted storage setup
4. Bloc observer setup
5. Orientation lock
6. URL strategy (web)
7. `runApp()`

### 10.2 `app/app.dart` — `MultiBlocProvider`

All blocs are registered in `MultiBlocProvider` in `app.dart`. Each service is given a `Dio` from `DioFactory`:

```dart
BlocProvider<<Feature>Bloc>(
  create: (context) => <Feature>Bloc(
    repository: <Feature>RepositoryImpl(
      <feature>Service: <Feature>Service(
        dio: DioFactory.create(authenticated: true),   // false for OTP/login services
      ),
    ),
  ),
),
```

**Rules:**
- Each service receives a `Dio` from `DioFactory.create(authenticated: …)` — the factory applies the shared base options + interceptors, so services no longer hand-configure Dio.
- Use `authenticated: false` for unauthenticated services (e.g., the OTP/login service) so `AuthInterceptor` is omitted.
- If a bloc depends on another bloc, use `BlocProvider.of<OtherBloc>(context)` inside the `create` callback:

```dart
BlocProvider<DependentBloc>(
  create: (context) => DependentBloc(
    otherBloc: BlocProvider.of<OtherBloc>(context),
    repository: ...,
  ),
),
```

- The order of `BlocProvider` registration matters — a bloc must be registered **before** any other bloc that depends on it.
- Use `lazy: false` only when a bloc must initialize immediately on app start (e.g., `DeviceBloc`).
- Dispatch initialization events using the cascade operator: `..add(const InitEvent())`.

### 10.3 `MaterialApp` & Theme

The root `Application` widget in `app.dart` returns the single `MaterialApp` (wrapped by the `MultiBlocProvider`). It wires the theme from `AppTheme` (§9.4) and the router from GoRouter (§11):

```dart
// lib/app/app.dart
return MaterialApp.router(
  debugShowCheckedModeBanner: false,
  theme: AppTheme.lightTheme,
  darkTheme: AppTheme.darkTheme,
  themeMode: ThemeMode.system,   // or from a ThemeBloc/Cubit (HydratedBloc)
  routerConfig: appRouter,
  // localizationsDelegates / supportedLocales added here if l10n is used
);
```

**Rules:**
- There is exactly ONE `MaterialApp`, and it lives in `app.dart` — never build a second one elsewhere.
- Theme values come ONLY from `AppTheme`; never pass an inline `ThemeData` here.
- For a user-selectable theme, wrap the `MaterialApp` in a `BlocBuilder<ThemeBloc, ThemeState>` and pass `state.themeMode`.

## 11. Routing — GoRouter

> **Every time a new screen is added, BOTH `routes.dart` and `app_router.dart` MUST be updated.** This is mandatory — no screen is reachable without a registered route.

### 11.1 `routes.dart` — Route Name Constants

Every route name is a `const String` in `lib/core/route/routes.dart`. Add a new one for every new screen:

```dart
// routes.dart
const String authRoute = 'auth';
const String homeRoute = 'home';
const String verifyOTPRoute = 'verify-otp';
const String <newFeature>Route = '<new-feature>';  // ← add this for every new screen
```

**Rules:**
- Route name values are `kebab-case` strings (lowercase with hyphens).
- Constant names are `camelCase` with `Route` suffix.
- Never use a hardcoded string for navigation — always reference the constant.

---

### 11.2 `app_router.dart` — GoRoute Registration

Every route constant must have a matching `GoRoute` inside `app_router.dart`. Add new routes inside the existing `routes: [...]` list:

```dart
// Inside app_router.dart routes list:
GoRoute(
  name: <newFeature>Route,
  path: '/<new-feature>',
  builder: (context, state) => const <NewFeature>Page(),
),

// With query parameters:
GoRoute(
  name: verifyOTPRoute,
  path: '/verify-otp',
  builder: (context, state) {
    final phone = state.uri.queryParameters['phone'] ?? '';
    return VerifyOTPPage(phone: phone);
  },
),

// Nested routes (child of parent):
GoRoute(
  name: parentRoute,
  path: '/parent',
  builder: (context, state) => const ParentPage(),
  routes: [
    GoRoute(
      name: childRoute,
      path: 'child',   // ← no leading slash for nested routes
      builder: (context, state) => const ChildPage(),
    ),
  ],
),
```

**Rules:**
- Path values start with `/` for top-level routes, **no** leading slash for nested routes.
- Always use `name:` parameter — never navigate by path string.
- Route guards (`redirect`) belong in `app_router.dart`, not in individual screens.
- Shell routes (bottom nav, drawer) use `ShellRoute` — wrap child routes inside.
- Keep imports in `app_router.dart` alphabetically sorted by feature name.

---

### 11.3 Navigation API — Always Use Named Routes

```dart
// Push a new screen onto the stack:
context.pushNamed(verifyOTPRoute);

// Replace current screen (no back button):
context.pushReplacementNamed(homeRoute);

// Go to a screen and clear the entire stack:
context.goNamed(homeRoute);

// With query parameters:
context.pushNamed(
  verifyOTPRoute,
  queryParameters: {'phone': phone.text.trim()},
);

// With path parameters:
context.pushNamed(
  orderDetailRoute,
  pathParameters: {'id': orderId},
);

// Pop back:
context.pop();

// Pop with a result value:
context.pop(result);
```

**Never use:**
- `Navigator.of(context).push(...)` or `Navigator.push(...)`
- Raw path strings: `context.go('/home')`
- `MaterialPageRoute` directly in screens

## 13. Error Handling Rules

1. **Service layer**: Wrap the generated client call in `try/catch` with the two failure layers:
   - Success path → wrap the returned DTO with `JsonResponse.success(data: dto)`
   - `on DioException catch (error)` → use `DioExceptionOf.exceptionFromDioError(error).errorMessage` (the generated client throws `DioException` on non-2xx)
   - `on Exception` → generic fallback

2. **Bloc layer**: Wrap the `await repository.method()` in `try/catch (_)` — emit `<Feature>Failure` (or `state.copyWith(error: …)`) in catch.

3. **UI layer**: Always show errors via `SnackBar` with `Theme.of(context).colorScheme.error` background. Never use `AlertDialog` for transient API errors.

4. **Never** `print()` errors. Use the `AppBlocObserver` for bloc event/state logging (already configured — do not touch).

5. **Never** let a raw `DioException` leak out of the Service — it must always become a `JsonResponse`.

## 14. Equatable Rules

- **Generated DTOs** (`data/api/models/`): **freezed**, NOT `Equatable`. freezed already implements value equality (`==`/`hashCode`) — do **not** add `Equatable` to them.
- **Hand-written domain models** (`data/models/`): Always extend `Equatable`. Override `get props` with ALL fields.
- **States**: Always extend `Equatable`. Override `get props` only in states that carry data.
- **Events**: Always extend `Equatable`. Override `get props` with all event parameters.
- **Params/Entity** (`data/entity/`): Do **NOT** extend `Equatable` — these are mutable request objects.
- Use `List<Object?>` (with nullable) when any field can be null. Use `List<Object>` when all fields are non-null.

## 16. What is Strictly Forbidden

- ❌ Hand-editing anything under `lib/data/api/`, any generated model, or any `*.g.dart` / `*.freezed.dart` file — change the canonical spec and regenerate.
- ❌ Hand-writing an API model, client method, or params class for an endpoint/schema that exists (or should exist) in the OpenAPI contract — add it to the spec and regenerate instead.
- ❌ Making raw `dio.get/post/...` calls in a service for an endpoint the spec can describe — call the generated client method.
- ❌ Calling the generated `RestClient` directly from a bloc or UI — always go Service → Repository → Bloc.
- ❌ Letting a raw `DioException` escape the Service — it must become a `JsonResponse`.
- ❌ Adding interceptors or timeouts inside a service — that belongs in `DioFactory`.
- ❌ Using `setState` for any logic that is managed by BLoC — `setState` is allowed only for purely local UI state (e.g., form validation flag, animation controller).
- ❌ Calling `context.read<>()` or `BlocProvider.of<>()` at the top level of `build()` — only call inside callbacks or use `BlocBuilder`/`BlocConsumer`.
- ❌ Hardcoded colors (`Colors.red`, `Colors.blue`, etc.) in screens or widgets.
- ❌ Putting business logic inside repository `Impl` — the impl delegates directly to the service.
- ❌ Making HTTP calls directly from a bloc — all HTTP goes through generated client → service → repository → bloc.
- ❌ Throwing exceptions from repositories or blocs — catch them and emit failure states.
- ❌ Using raw `Navigator.push()` — always use GoRouter named routes.
- ❌ Modifying any file inside `core/interceptors/`, `core/utils/`, `core/exceptions/`, `core/environments/`, or `debug/`.
- ❌ Importing Firebase packages outside of `start.dart`, `firebase_options.dart`, and services that explicitly need them (e.g., for FCM token).
- ❌ Creating a bloc state that doesn't follow either Style A (single class with `isLoading`/`error`/`message`/`copyWith`) or Style B (abstract base + Initial/Loading/Success/Failure subclasses).
- ❌ Leaving `catch` blocks empty — always emit a failure state or log the error.
- ❌ Using `dynamic` as a variable type when the type is known.
- ❌ Adding `Equatable` to generated freezed DTOs.
- ✅ Prefer explicit typing when it improves readability or architectural clarity.
- ✅ Use `var` only when the type is obvious from the right-hand side.

## 17. Quick Reference Checklist

When creating a new feature, follow this exact order:

- [ ] **Spec** → add/update the endpoint(s) + schema(s) in `backend/openapi/openapi.json`
- [ ] **Generate** → run `make -f files/Makefile generate-api` from the repository root (synchronizes each app's local spec and produces Freezed models + Retrofit/Dio clients in `lib/data/api/`)
- [ ] **Params** (only if not in the spec) → `lib/data/entity/<feature>_params.dart` (mutable, `toJson`, `copyWith`)
- [ ] **Service** → write a thin adapter in `lib/data/services/<feature>_service.dart` that calls the generated client and maps its typed result or `DioException`; do not duplicate endpoint declarations or DTOs
- [ ] **Repository** → `lib/data/repositories/<feature>_repository.dart` (abstract + impl — delegates to the service)
- [ ] **BLoC** → `lib/bloc/<feature>/` (3 files: bloc, event, state — Style A or B)
- [ ] **Register BLoC** → `lib/app/app.dart` `MultiBlocProvider` list, injecting `DioFactory.create(...)` (in correct dependency order)
- [ ] **Screen** → `lib/view/screens/<feature>/<screen>.dart` (BlocConsumer, themed, no hardcoded colors)
- [ ] **Route** → Add route name to `lib/core/route/routes.dart`, add `GoRoute` to `app_router.dart`

> **List / feed / search features** additionally follow **§3.8 Pagination** (`page`/`limit`/`hasMore`/`isLoadingMore`, accumulate, reset-on-query, 80% scroll trigger) and **§3.9 Search Debounce** (500 ms, min 3 chars, skip-while-loading). The repository stays a pure delegate (**§4.2**) — paging/merging logic lives in the bloc.

## 18. Modern Flutter / Dart Syntax (No Deprecated APIs)

> Target current stable Flutter/Dart. Do **not** introduce deprecated members. Run `flutter analyze` and `dart fix --apply` before finishing so the tree stays warning-clean.

### 18.1 Color opacity — `withValues`, not `withOpacity`

`Color.withOpacity()` is **deprecated** (Flutter 3.27+) because alpha is now a floating-point value and `withOpacity` quantizes it, losing precision. Use `withValues(alpha:)`.

```dart
// ❌ Deprecated
color.withOpacity(0.5)
someColor.opacity                              // getter also deprecated
Color.fromARGB(255, 66, 133, 244)

// ✅ Current
color.withValues(alpha: 0.5)
someColor.a                                    // read the alpha channel directly
Color.from(alpha: 1.0, red: 0.26, green: 0.52, blue: 0.96)   // normalized floats
```

- Replace **every** `withOpacity(x)` with `withValues(alpha: x)`.
- Use `color.a` (not `color.opacity`) to read alpha; prefer `Color.from(...)` over `Color.fromARGB(...)` for new code.
- `dart fix --apply` migrates existing `withOpacity` calls automatically.

### 18.2 Avoid Dart dot shorthands while codegen uses analyzer 7.x

Dart dot shorthands are supported by the current SDK, but this project cannot use them yet. `retrofit_generator` 9.7.0 constrains codegen to analyzer 7.x; dot-shorthand syntax in a project file or dependency can make `build_runner` abort with `Missing implementation of visitDotShorthandInvocation`. Keep explicit type names until the generator/analyzer chain is upgraded.

```dart
// ✅ Required explicit form
padding: EdgeInsets.all(16)
padding: EdgeInsets.symmetric(horizontal: 16, vertical: 8)
borderRadius: BorderRadius.circular(12)
mainAxisAlignment: MainAxisAlignment.center
crossAxisAlignment: CrossAxisAlignment.start
fontWeight: FontWeight.bold

// ❌ Do not use yet (breaks the pinned codegen analyzer)
padding: .all(16)
padding: .symmetric(horizontal: 16, vertical: 8)
borderRadius: .circular(12)
mainAxisAlignment: .center
crossAxisAlignment: .start
fontWeight: .bold
```

**Rules:**
- Use explicit constructors and enum types in every hand-written Dart file.
- Check new dependencies immediately with `dart run build_runner build --delete-conflicting-outputs`; dependencies containing dot shorthands can trigger the same crash.
- `package_info_plus` is pinned below 10 because v10 pulls `win32` 6.x, which contains the incompatible syntax.
- Revisit this rule only after upgrading `retrofit_generator` and its analyzer constraint, then regenerating and verifying the complete project.

### 18.3 General currency rule

- Never add a member the analyzer flags as deprecated — find the current replacement first.
- Match the API surface to the Flutter/Dart version already pinned in `pubspec.yaml`; don't assume a newer API than the project is on.
- Prefer Material 3 theming (`useMaterial3: true`, already set in `AppTheme`) and the current color APIs (`withValues`, `Color.from`) throughout.
